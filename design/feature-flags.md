# Maven 4 Feature Flags Pattern

This document describes the `Features` pattern for feature flags and warning suppression properties.

## Adding a New Feature Property

1. Add a constant in `api/maven-api-core/.../Constants.java` with `@Config(type = "java.lang.Boolean")`.
2. Add a static method in `api/maven-api-core/.../feature/Features.java` using `doGet(userProperties, constant, default)`.
3. When the feature is a refinement of `maven3Personality`, use `mavenMaven3Personality(userProperties)` as the dynamic default.

```java
// Constants.java
@Config(type = "java.lang.Boolean")
public static final String MAVEN_LIFECYCLE_SEQUENTIAL_PHASES = "maven.lifecycle.sequentialPhases";

// Features.java
public static boolean sequentialLifecyclePhases(@Nullable Map<String, ?> userProperties) {
    return doGet(userProperties, Constants.MAVEN_LIFECYCLE_SEQUENTIAL_PHASES,
            mavenMaven3Personality(userProperties));
}
```

Don't hardcode `Features.mavenMaven3Personality()` when a behavior could be independently toggled. Introduce a dedicated property with `maven3Personality` as the default fallback.

## Warning Suppression Properties

When a PR changes Maven behavior, use a **warning suppression property** rather than a feature flag to revert behavior:

- **Feature flag to revert behavior** — only when reasonable people disagree whether the change is correct. Never add a flag to re-enable a confirmed bug.
- **Warning suppression property** — always when emitting a warning about a changed element.

Every warning must include:
1. What was dropped or changed.
2. How to fix it properly.
3. The `-D` property to suppress.

```java
@Config(type = "java.lang.Boolean", defaultValue = "true")
public static final String MAVEN_WARN_SOMETHING = "maven.warn.something";
```

## FATAL vs WARNING: Where the Fix Belongs

Maven 4's `[FATAL]` for an explicit `<relativePath>` that resolves to the wrong artifact is intentional strictness. Before proposing a leniency workaround:

1. Is the bad value generated by a third-party tool? → fix belongs in that tool.
2. Are published POMs affected? → if no, the tool fix is sufficient.
3. Is the tool fix available? → timing issue, still doesn't justify permanent leniency.

**Rule:** only add Maven-side leniency when Maven itself created the ambiguity.
